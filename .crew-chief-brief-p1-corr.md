# Correction Brief — Piece 1: recarregar recria thread do serviço

## Previous attempt
The previous executor refactored `ServicoHandle` to store `DescritorServico` (good preparatory work) but did NOT implement the actual fix: after `parar(id)` followed by `repetir(id)`, the service must return to `Subindo`/`Ok` with a **new PID**. No test was added.

## What you must do NOW
Build on the existing refactor in this branch. The handle already stores `desc: DescritorServico`. Use it to re-spawn the supervisor thread when needed.

### Required behavior
When `repetir(id)` is called and the service's thread has already terminated (`terminou == true`):
1. Reset `parar`, `reiniciar`, and `terminou` flags on the handle.
2. Spawn a NEW supervisor thread using the stored `desc`.
3. The new thread must run `loop_servico` exactly like `iniciar()` does.
4. `foto(id)` must reflect the new PID once the service is up.

If the thread is still alive when `repetir` is called, the existing signal-based behavior must be preserved (no double-spawn).

### Implementation approach
Add a method like `ServicoHandle::reanimar_se_morto(&self) -> Result<(), String>` that:
- Checks `terminou.load(Ordering::SeqCst)`; if false, returns Ok (thread still alive, signal suffices).
- If true, resets the three atomics and spawns a new thread with `self.desc.clone()`.
- Call this from `repetir()` after setting the reiniciar signal.

Alternatively, modify `repetir()` directly to check and re-spawn. Choose whichever integrates cleanly with the existing code.

### Test requirement (MANDATORY)
Add a test in `servicos.rs::testes` named `repetir_apos_parar_recria_thread_com_novo_pid` that:
1. Starts a fake HTTP child via `criar_filho_http_falso` on a free port.
2. Registers it as a service via `iniciar()` (or constructs a `ServicoHandle` + spawns the loop manually if `iniciar` requires full infra).
3. Calls `parar(id)` and waits until `terminou` is true (poll `foto()` or the atomic).
4. Calls `repetir(id)`.
5. Asserts that within a reasonable timeout the service responds to `/saude` again with a **different PID** than before.

Use the existing test helpers (`porta_livre`, `criar_filho_http_falso`, `esperar_saude`). Clean up the child process in a Drop guard.
